# Protalone 架構說明

這份說明用繁體中文寫下已落地的架構，以及每位使用者如何擁有自己的登入與自己的網站清單。英文產品規格在 [PLAN.md](PLAN.md)。

## 產品邊界

Protalone 是個人啟動頁。

- **Explore** 是公開目錄，收錄約 129 個常用網站，未登入也能搜尋和打開。
- **My Portal** 是私人清單。只有登入的那一個帳號能看見、修改自己的群組、釘選和收藏。
- 收藏不會被寫進公開目錄。
- 文章剪藏不在這個產品裡。

「command visited」理解成平常會打開的網站。畫面上的快速開啟做同一件事：打幾個字，按 Enter，網站在新分頁打開。按 `/` 可以聚焦搜尋框。

## 為什麼是這個形狀

1. **畫面用 Next.js App Router。** 目錄和入口由伺服器元件直接讀資料，變更走 Server Actions。瀏覽器不連接資料庫，也不能自己宣稱「我是哪一個 user id」。
2. **身份用電子郵件加密碼。** 原計畫的魔法連結需要寄信服務。每個電子郵件是一個帳號，密碼只存 scrypt 加鹽雜湊。之後若改成魔法連結或 Supabase Auth，換掉的只是「如何證明你擁有這個電子郵件」。入口資料仍然掛在同一個 user id 上。
3. **資料用 SQLite 檔，給單一行程的 Node。** 這個環境沒有 Docker，也沒有現成的託管資料庫。SQLite 讓註冊、登入和隔離現在就能運作。它不適合放到會清掉磁碟的無狀態主機。若以後要多台伺服器，把同一套表搬到 Postgres，並加上列層級安全（RLS）。應用程式仍然從 session 取 user id。
4. **目錄和私人收藏分表。** 目錄沒有 user_id，任何人可讀，只有種子匯入會寫。私人表每一列都有 user_id。
5. **伺服器不去抓使用者貼上的網址。** 標題來自目錄或使用者自己填的字。圖示只用主機名稱，向固定的 favicon 服務索取。伺服器不會連到使用者貼上的內網位址。

資料表名叫 `link_groups`，避免和 SQL 的 `GROUP` 搞混。它仍是一層群組。

## 每個帳號如何登入

### 帳號

- `users` 一列就是一個人。
- 電子郵件會先去掉前後空白、再轉成小寫，然後必須唯一。`Ada@Example.com` 和 `ada@example.com` 是同一個帳號。
- 密碼長度 8 到 200。資料庫不存密碼，只存 `鹽:scrypt雜湊`。比對時用固定時間比較，減少從回應時間猜密碼的空間。
- 信箱不存在時，仍會對一組假雜湊做一次 scrypt，避免「這個信箱沒有註冊」比「密碼錯誤」回得更快。
- 登入失敗的訊息一律是「Email or password is wrong.」，不透露信箱是否存在。
- 同一個信箱連續失敗 8 次，會暫停再試 5 分鐘。這個計數記在這一個行程的記憶體裡。

### 登入之後伺服器怎樣認得你

1. 密碼正確之後，產生 32 bytes 的隨機 token。
2. Cookie `protalone_session` 只放這個 token。資料庫的 `sessions.token_hash` 存 SHA-256，不存 token 本身。資料庫檔案外洩時，不能直接把欄位貼進 cookie 使用。
3. Cookie 是 HttpOnly，頁面上的 JavaScript 讀不到。SameSite 是 Lax。正式環境預設加上 Secure。本機用 http 測試時不要強制 Secure，否則瀏覽器不會保存 cookie。
4. Session 效期 30 天。過期的列會在下次查找時刪除。
5. 之後每一個請求都由伺服器讀 cookie、計算雜湊、找到尚未過期的 session，得到唯一的 user id。
6. 登出只刪現在這一筆 session，並清掉 cookie。另一台裝置上的登入還在。

### 為什麼不能相信瀏覽器傳來的使用者 id

表單、網址和隱藏欄位都可以改。Server Actions 和 `/go/[id]` 不接受客戶端指定的 user id。它們只呼叫 `getCurrentUser()`。私人讀寫函式的 SQL 一律是 `where user_id = ?`，這個問號來自 session。

你現在是誰，只由那枚 HttpOnly cookie 決定。

### 兩個人同時使用

- 兩個瀏覽器可以同時登入兩個帳號。各有一枚 cookie，各對到自己的 session，各看到自己的入口。
- 同一個瀏覽器要換人：先登出，再用另一個電子郵件登入。新 cookie 指向新的 user id，入口內容整個換人。
- 用同一個電子郵件再登入，仍是原來的 user id，收藏還在。這是帳號，不是這一次瀏覽。

### 具體擋下的越權

- B 已登入，卻打開 A 的 `/go/[id]`：查詢是 `id` 加上 B 的 `user_id`。對不上就 404，不會轉到 A 的網址，也不會增加 A 的開啟次數。
- 尚未登入就打開 `/go/[id]`：先去登入頁。登入之後再查一次所有權。
- B 試著把連結放進 A 的群組：群組必須 `id` 和 `user_id` 都屬於 B。別人的群組 id 會被拒絕。
- B 的入口列表只查 B 的 `user_id`。
- 刪除使用者時，他的 session、群組和收藏會跟著刪除。目錄不受影響。刪除群組只會把該群組裡的收藏改成未分組，不刪網址。

### 和資料庫 RLS 的關係

Supabase 會在資料庫再擋一次：`auth.uid() = user_id`。就算程式漏了條件，資料庫也回傳零列。

SQLite 沒有登入者的 `auth.uid()`。現在的做法是把私人資料收進 `lib/portal.ts` 和 `lib/accounts.ts`，這些函式強制帶上從 session 取出的 user id。跨帳號測試會建立兩個使用者，證明第二個人讀不到、搬不走、也開不了第一個人的收藏。

以後搬到 Postgres 時，保留同樣的欄位，加上 RLS，就是第二道牆。產品行為不用改。

### 登入頁和導向

- `/signup` 建立帳號，`/signin` 登入已有帳號。
- 未登入開 `/` 會到 Explore。已登入開 `/` 會到自己的 Portal。
- `/portal` 沒有 session 會去登入，登入後回到 `/portal`。
- `next` 只允許站內相對路徑。`https://`、`//` 和換行都會被丟掉，避免登入後被帶去別的網站。
- Server Actions 會檢查請求來源。配合 SameSite=Lax，別的網站不容易代你修改收藏。

## 網址規則

只接受 http 和 https。主機轉小寫，去掉片段、預設埠、使用者名稱和密碼，以及 `utm_*`、`fbclid`、`gclid`、`mc_cid`、`mc_eid`。路徑結尾的斜線會去掉，但網站根目錄保留。同一位使用者的正規化網址只能有一筆收藏。再存一次會回到原本那一筆。

## 目錄

種子在 `catalog/catalog.json`。第一次啟動若分類是空的，會匯入這份種子。之後改檔再執行 `npm run import-catalog`，會依網址更新名稱和描述，不會清掉使用者的收藏。

## 測試

- 網址正規化、站內導向、搜尋裡的 `%` 被當成普通字。
- 兩個帳號的隔離、群組刪除、session 只存雜湊並且會過期、刪除使用者時私人資料一併消失。

網域、一週的日常使用，以及改成 Postgres RLS，留到這個單機版本真的被天天打開之後。
